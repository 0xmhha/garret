# Services specification

Status: approved. Services are the business operations of garret.
Each one coordinates components ([components.md](components.md)) inside one
write transaction or one unit of work, writes its audit event in the same
transaction, and publishes real-time events only after the commit
([data.md section 6](data.md#6-write-operations)). Transport (stage 5) turns
requests into service calls and never touches the store directly.

## 1. Rules for every service

1. **Authorization is checked in the service**, not only in the handler or the
   UI (security.md, Authorization). Every operation takes the acting user as
   its first argument after `ctx` and returns `ErrForbidden` before touching
   data when the user may not act.
2. **Validation before the transaction.** Lengths, formats and enumerations
   are checked in Go first, so a constraint violation in SQLite means a bug,
   not user input.
3. **No I/O inside a write transaction** other than SQLite itself. Git work
   (merge base, commit lists, ref pinning) runs before or after, as data.md
   6.2 describes.
4. **Errors are typed.** Each service exports sentinel errors (`ErrNotFound`,
   `ErrConflict`, `ErrForbidden`, `ErrInvalid` with a field name). Transport
   maps them to the API error codes.
5. **Time and IDs are injected** (`clock.Clock`, `*id.Generator`); randomness
   is `crypto/rand.Reader` in production.
6. **Queries** live in `internal/store/queries/<service>.sql` and are
   generated by sqlc. Each query is added together with the service method
   that uses it and a test that runs it.
7. **Audit events** use dotted actions (`review.created`). Their `data` never
   contains secrets or content bodies.

Carried requirements from earlier security reviews:

- `VerifyPassword` callers reject on any error and on `ok == false`;
  `ValidPassword` runs before `HashPassword`.
- Certificates are issued only from `ClientTemplate`; only `PublicKey` is
  taken from a certificate request. Serials are stored with `SerialString`.
- `ActiveSerials.Replace` runs after every commit that issues or revokes a
  client certificate, and once at startup before any listener accepts.

## 2. Audit and events (`internal/audit`, `internal/realtime`)

- `audit.Record(ctx, tx, Event)` inserts one `audit_events` row inside the
  caller's transaction. It is the only writer of that table.
- `realtime.Hub` implements data.md 7.6: one goroutine owns the connection
  set; `Publish(Event)` is non-blocking (a full hub channel drops the event
  and counts it); each connection has a bounded buffer and is closed when it
  is full. An event with a target user (notifications) reaches only that
  user's connections. Events carry only the type and the resource identifiers
  (api.md, WebSocket channels). The hub delivers an event only to
  connections of users who can see its project.

## 3. Accounts and devices (`internal/auth`)

### 3.1 First administrator

`SetupAdmin(ctx, setupToken, username, displayName, password, csrDER, device)`
runs only while no administrator exists. The setup token is a `NewSecret`
value held in memory, printed once at start, single use. It creates the
user, issues a client certificate with `issued_via = setup`, and records
`user.created` and `certificate.issued`.

### 3.2 Invitations

- `CreateInvitation(ctx, admin, role)` returns the token once; the row stores
  its digest. Lifetime 30 minutes; the code is six words from the EFF
  large wordlist (transport.md, T-D3).
- `RevokeInvitation`, `ListInvitations`.
- `OpenInvitations(ctx) (bool, error)`: whether any invitation is unused,
  unrevoked and unexpired. The enrollment listener (stage 5) opens and closes
  on it, and also when the earliest open invitation expires.

### 3.3 Enrollment

`Enroll(ctx, token, username, displayName, password, csrDER, device)`
follows data.md 6.1 in one transaction: find the invitation by digest,
require it unused, unrevoked and unexpired, create the user, issue the
certificate, mark the invitation used (`WHERE used_at IS NULL`). A taken
username or a concurrently used invitation fails with no rows written. The
same error is returned for an unknown, expired, revoked or used token, so
the response does not reveal which.

### 3.4 Sessions

- `Login(ctx, username, password, certSerial, remote)`: rate-limited (Q1).
  The limiter reserves the attempt under one lock before the password is
  checked and gives it back on success, so concurrent requests cannot all
  pass the limit before any failure is counted;
  the user must exist, be enabled and match the client certificate's user
  when certificates are on. Creates a session (cookie secret and CSRF
  secret, digests stored). If `VerifyPassword` asks for a rehash, the new
  hash is stored in the same transaction. A wrong username and a wrong
  password take the same time and return the same error: a dummy hash is
  verified for unknown users.
- `Authenticate(ctx, sessionSecret, certSerial)`: valid while
  `now < expires_at` and `now − last_seen_at < 7 days`; the absolute limit
  is 30 days (security.md). `last_seen_at` is written at most once per
  minute. A session whose user differs from the certificate's user is
  rejected.
- `Logout` deletes the session row.
- A sweep deletes expired sessions hourly.

### 3.5 Personal access tokens

`CreateToken(ctx, user, name)` returns the token once. `AuthenticateToken(ctx,
username, token, certSerial, remote)` is used by the Git endpoint: rate
limited like login, constant-time digest comparison, same user as the
certificate, `last_used_at` at most once per minute. `RevokeToken`.

### 3.6 Certificates

- `RenewCertificate(ctx, user, currentSerial, csrDER, device)`: the current
  certificate must be active, unexpired, unrevoked and belong to `user`.
  Issues a new certificate with `issued_via = renewal` and
  `renewed_from = currentSerial`. The old certificate stays valid until it
  expires, so a renewal job that crashes after the response does not lock
  the device out. The checks run again inside the write transaction, so a
  revocation or a disable that commits in between cannot be bypassed.
- `ListCertificates`, `RevokeCertificate` (own devices, or any as admin).
- `DisableUser(ctx, admin, userID)`: sets `disabled_at`, deletes sessions,
  revokes tokens and certificates in one transaction, then replaces the
  active serials and closes the user's connections. The last enabled
  administrator cannot be disabled (`ErrConflict`), so setup never reopens
  by accident.

## 4. Projects (`internal/project`)

- `Create(ctx, admin, name, description)`: validates the name, creates the
  repository directory exclusively (`os.Mkdir`, under a per-name lock), runs
  `Runner.InitBare` in it, then inserts the row. If the insert fails, the new
  directory is removed. Creating the directory exclusively matters because
  `git init --bare` succeeds on an existing repository: without it, a
  failed duplicate create would remove the first project's repository. A repository
  directory that exists without a row (left by a crash) is removed at start
  (data.md 6.6).
- `List`, `Get` (with the clone URL), `Branches` (`Runner.Refs`).

## 5. Reviews (`internal/review`)

### 5.1 Opening and pushes

- `Open(ctx, user, project, sourceBranch, targetBranch, title)`: both
  branches must exist and differ. Outside the transaction: resolve heads,
  merge base and commits (500 at most, else `commits_omitted`). In the
  transaction: allocate the number from `next_review_number`, create the
  description document, the review and revision 1. After commit: pin
  `refs/garret/reviews/<id>/revisions/1`, publish `review.created`.
- `HandlePush(ctx, project, pusher, changes)`: called by the Git endpoint
  after `git-receive-pack` with the refs whose heads changed. For each open
  review on a changed source branch, under the review's keyed lock, follows
  data.md 6.2. A deleted source branch abandons nothing; the review stays
  open and shows the branch as missing. A push that resets the branch to its
  target (no commits left) adds no revision. If the target branch was
  deleted, the new revision keeps the previous base. A branch with no
  commits beyond its target cannot be opened for review (`ErrInvalid`).
  Commit subjects and author names are cut to 200 characters.
- At start, missing revision refs are re-created from `revisions.head_sha`.

### 5.2 Verdicts and state

- `RecordVerdict(ctx, user, review, value)`: on the latest revision, only
  while the review is open. The author may not approve their own review
  (Q2).
- `ChangeState(ctx, user, review, from, to)`: transitions `open → completed`,
  `open → abandoned`, `completed → open`, `abandoned → open`, conditional on
  the expected `from`. Who may change state is Q3.

### 5.3 Diffs and porting

- `Diff(ctx, user, review, view)` for the four views of architecture.md.
  Results are cached by `(from, to, path)` in a bounded cache (Q4). Binary
  files and files over the limits of atomic.md Q5 are reported, not diffed.
  A revision pair with different bases returns a notice flag.
- `Threads(ctx, user, review, atRevision)` returns comment threads; for a
  later revision than the anchor, unresolved code comments are ported with
  `ChangeBlocks` and `Port` over the diff from the anchor's head to the
  requested head (old-side comments over the bases). Porting is computed on
  read and never stored. A renamed file keeps its comments under the new
  path; a deleted file drops them from later revisions; a binary file or
  one over the diff limits makes them file-level comments.
- Commits named in a view or a file diff must belong to the review: a
  revision's base, head or one of its commits. A range must lie inside one
  revision, in order.
- Notifications: a verdict notifies the review's author; a new revision
  notifies everyone who gave a verdict or commented on the review, except
  the pusher.

## 6. Comments and discussions (`internal/comment`, `internal/discussion`)

- `CreateComment(ctx, user, parent, anchor, body, attachmentIDs)`: an anchor
  is accepted only on a review root comment; its path must exist at the
  anchored side's commit and its lines must lie inside that file. The
  anchor's commits must fit its view: `revision` is the revision's base and
  head; `commit` is a commit of the revision and its parent; `range` is two
  points of the revision in order. Mentions (Q5) and replies create
  notifications in the same transaction. Each user is notified at most once
  per comment, never for their own action, in this order: mention, reply to
  their thread, comment on their review. Replies go to a thread's root only
  and are never anchored.
- `EditComment(ctx, user, id, expectedVersion, body)`: author only,
  optimistic (`ErrConflict` on a stale version).
- `ResolveThread(ctx, user, rootID, resolved)`: who may resolve is Q3.
- `DeleteComment`: author or administrator; soft delete.
- `CreateDiscussion`, `RenameDiscussion`, `DeleteDiscussion` (soft). Rename
  and delete are for the author or an administrator.
- Edits notify only users mentioned in the new body and not in the previous
  version.
- Body limits from data.md: 1–65,536 bytes of UTF-8.

## 7. Collaborative documents (`internal/collab`)

Decision S4-D1 (this stage): `github.com/reearth/ygo` v1.55.0, using only its
`crdt` and `sync` packages, which add one module to the build. A spike
confirmed sync, convergence of concurrent edits and rebuilding from a
checkpoint plus later updates. The spike's claim that malformed updates are
rejected without a panic was wrong: the security review found an 18-byte
update (a subdocument guid that is not UTF-8) that makes
`EncodeStateVectorFromUpdate` panic. Every call into ygo therefore runs
inside a recover that turns a panic into an error, and the owner loop
recovers per message, so crafted input costs the sender its connection and
never stops the server. The sync package is transport-agnostic, so garret serves it from its
own authenticated WebSocket handler instead of ygo's bundled server. The
library is mostly maintained by one person; the version is pinned, and every
update pull request reviews the upstream changes before merging. If panics
keep appearing in testing despite the guard, the fallback is a fork that
carries the fix and follows upstream releases, dropped and archived once
upstream ships its own fix (transport.md, T-D4).

- One **owner goroutine** per loaded document (data.md 7.5) holds the
  `crdt.Doc` and a bounded inbox. Shared types are obtained once at load,
  outside any transaction: calling `GetText` inside `Transact` deadlocks
  (found in the spike).
- **Join**: the handler registers a connection with the owner, which sends
  sync step 1 and answers the client's step 1.
- **Update**: data.md 6.5. An update over 1 MiB, one that does not parse, or
  one that makes the library panic is rejected and the connection closed;
  nothing is stored. An update that parses but then fails to apply is
  already stored: it is logged, skipped again on reload, and the document
  state stays the same on every load.
- **Generations**: a client joins with the generation it loaded; an older
  one gets `ErrStale`. `Rebuild` (erasure) deletes every update and
  checkpoint, increments the generation, stores one checkpoint of a new
  document holding only the cleaned text, runs the caller's erasure record in
  the same transaction, then sends connected clients message type 2
  (reload) and disconnects them. A client that still held the erased text
  cannot push it back without loading the new generation first.
- **Joining**: a deleted discussion's body cannot be joined. A join queued
  while the document unloads is always served, because the owner unloads
  only when its queue is empty, under the lock joins queue under.
- **Checkpoint** after a quiet period (Q6): encoded state, extracted text,
  contributors since the previous checkpoint. Mention detection runs on the
  checkpoint text and notifies only newly mentioned users.
- **Unload** after the last client leaves and a grace period passes (Q6), or
  on shutdown after a final checkpoint.
- **Awareness** messages (cursors, names) are relayed to the document's
  other connections and never stored.
- **Framing**: messages use the y-websocket framing, a first byte of 0 for
  sync and 1 for awareness. The document's content is the `Y.Text` named
  `body`; the browser binds the same name.
- **Validation**: an update is parsed (`EncodeStateVectorFromUpdate`) before
  it is stored, so a malformed one closes the connection and stores
  nothing. An oversized update is refused before it reaches the owner.
- **Mentions in documents**: a user who contributed since the previous
  checkpoint is not notified, since they may have written the mention
  themselves.

## 8. Notifications (`internal/inbox`)

- Created by the services above inside their transactions, for the kinds in
  data.md (`mention`, `comment_on_my_review`, `reply_to_me`,
  `verdict_on_my_review`, `revision_on_reviewed`). A user is never notified
  of their own action.
- `List`, `MarkRead`; a daily sweep deletes notifications older than 90 days.

## 9. Attachments (`internal/attachment` service part)

`Upload(ctx, user, project, filename, r)`: stores the file
(`Store.Put`, 25 MiB), inserts the row with the detected media type and the
filename stripped of path separators and control characters, cut to 255
bytes on a character boundary, or `file` when nothing is left. A comment can
link attachments of its own project that are not deleted; lists show only
links whose attachment is not deleted. `Download`
checks that the user may see the project and serves the type only if
`Inline` allows it. `Delete` is a soft delete by the uploader or an
administrator.

## 10. Administration (`internal/admin`)

- `EraseComment`, `EraseAttachment`, `EraseDocument`: data.md 6.6, each with a
  required reason. Erasing an attachment removes the file only when no other
  attachment row of the project references the same digest.
- `Export(ctx, admin, project, w)` writes one archive (Q7): a Git bundle with
  every ref, one JSON file per table with the project's rows, and the
  attachment files. It records `project.exported` with the archive's SHA-256.
  The users table is exported as ID, username, display name, role and
  dates only, never password hashes. The bundle is written to a temporary
  file beside the repositories, not to the system temporary directory, and
  removed afterwards. Export remembers the project's latest audit event when
  it starts reading; if a newer event exists when it records the export, it
  fails with `ErrConflict`, so the archive never misses a write.
- `Purge(ctx, admin, project, typedName)`: requires `typedName` to equal the
  project name and a `project.exported` event newer than every other
  project event (Q8). Then data.md 6.6. Purge does not take the project's
  exclusive lock: every write goes through the one writer connection, and
  the purge transaction itself checks that the export is the project's last
  event, so a write that commits first makes the purge refuse, and a write
  that commits after finds no project and fails on its foreign key. The
  per-project lock stays available for later operations that need it.

## 11. Settled values

These were open questions in the draft and were accepted as proposed during
review.

| # | Question | Value |
|---|---|---|
| Q1 | Login and token rate limits | 10 failures per 15 minutes, counted per username and per source address; further attempts get the same error until the window passes |
| Q2 | May an author approve their own review | No. They may request changes |
| Q3 | Who may change review state and resolve threads | Any member; every change is recorded with its user and time |
| Q4 | Diff cache size | 256 entries and 64 MiB, whichever comes first |
| Q5 | Mention syntax | `@username` at a word boundary, matching an existing enabled user |
| Q6 | Collaborative document timings | Checkpoint after 30 s without updates; unload 60 s after the last client leaves |
| Q7 | Export archive format | One `.zip` file, readable on macOS without extra tools |
| Q8 | What makes an export "completed" for purge | A `project.exported` audit event newer than every other event of the project, so anything written after the export forces a new one |

Proposed defaults already in [security.md](../design/security.md#authentication)
(session 7 days idle and 30 days maximum) are used as
written.
